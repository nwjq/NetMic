# NetMic 项目运行模型

本文档是 NetMic 的总控文档。

它回答三个问题：

1. 项目靠什么文档体系长期运转
2. 一个改动如何从想法进入持续开发
3. 工作中发现的有效技巧如何进入正式复用机制

## 1. 文档分层

NetMic 的文档分为 5 层：

### A. 产品边界层

- `MVP.md`

作用：

- 定义产品目标、非目标、参数安全范围、协议边界、状态机边界

这是最上层边界，决定“能不能做”和“做到什么程度”。

### B. 运行模型层

- `docs/OPERATING_MODEL.md`

作用：

- 定义项目如何持续推进
- 定义文档之间的关系
- 定义改动如何进入主线
- 定义自我进化与 skill 沉淀机制

这是总控层，决定“项目怎么往前走”。

### C. 执行控制层

- `docs/HARNESS.md`
- `docs/ROADMAP.md`
- `docs/MODULE_OWNERS.md`

作用：

- `HARNESS`：定义双机执行链路、产物、结论口径
- `ROADMAP`：定义当前阶段顺序与每个里程碑的出口条件
- `MODULE_OWNERS`：定义模块边界与责任归属

这一层决定“当前该做什么，做完怎么算数，由谁做”。

### D. 接口与行为层

- `docs/PROTO.md`
- `docs/UI.md`

作用：

- 定义协议、消息、状态、IPC、UI 行为

这一层决定“系统如何对外表现和交互”。

### E. 现场与配置层

- `docs/ENV.md`
- `.harness/hosts.env`

作用：

- 定义运行时变量
- 接收用户补充的现场信息

这一层决定“在当前机器和网络环境里怎么落地”。

## 2. 单一工作主线

项目持续开发只走一条主线：

```text
确定当前里程碑
-> 确定本次工作包
-> 修改对应模块
-> 进入 Harness 验证
-> 生成产物与结论
-> 必要时沉淀 skill
-> 进入下一工作包
```

规则：

- 不允许脱离里程碑单独生长功能
- 不允许只有实现、没有 Harness 入口
- 不允许只有手工验证、没有统一产物
- 不允许只在对话里记住流程而不写入文档或 skill

## 3. 持续开发循环

每次工作循环都按以下顺序进行：

1. 读取边界
   - 先看 `MVP.md`
   - 再看 `docs/OPERATING_MODEL.md`
   - 再看当前相关的执行控制与接口文档
2. 判定当前主目标
   - 当前主目标始终是“第一个未完成的里程碑”
3. 切分工作包
   - 每个工作包只解决一个明确问题
   - 每个工作包必须能指向一个验证动作
4. 实现或补文档
   - 接口、边界、配置变更先改文档，再改实现
5. 进入 Harness
   - 通过统一执行链路完成验证
6. 输出结论
   - `pass`
   - `fail`
   - `blocked`
7. 处理复用机会
   - 若本次形成了稳定可复用技巧，则升级为 skill

## 4. 持续推进规则

项目默认持续推进，不因局部完成而停下。

规则：

- `pass`：表示当前工作包通过，随后立即进入下一个工作包
- `fail`：表示当前工作包未通过，随后继续进入修复循环
- `blocked`：只有当阻塞来自缺失现场配置、缺失用户补充信息、或当前环境无法继续执行时，才允许暂停并等待用户补充

允许停止的条件只有两类：

1. `docs/ROADMAP.md` 中所有里程碑都已跑通
2. 当前主线被真实配置阻塞，且该阻塞必须由用户补充或改变环境才能继续

除此之外，Agent 不应自行停止。

## 5. 工作包规则

一个合格的工作包必须同时回答：

- 属于哪个里程碑
- 归属哪个模块
- 改动后如何验证
- 产物会落在哪里
- 是否会影响协议、配置、UI、Harness 或 skill

如果回答不清，这个工作包就还没准备好进入开发。

## 6. Harness 在全局中的位置

Harness 不是整个项目，它是项目的统一执行面。

Harness 负责：

- 准备双机现场
- 驱动运行
- 收集产物
- 给出统一结论

Harness 不负责：

- 决定产品边界
- 决定里程碑顺序
- 决定模块归属
- 替代协议与 UI 文档

## 7. 里程碑推进规则

里程碑推进遵循：

- 总是优先推进第一个未完成里程碑
- 后续里程碑可以预留骨架，但不能抢占主线
- 只有进入 Harness 并形成稳定产物，才算该里程碑真正前进一步
- 某个工作包完成，不代表本轮工作结束；只有里程碑完成才允许切换到下一里程碑
- 某个里程碑完成，也不代表项目结束；应继续推进下一个未完成里程碑

当前的推进顺序由 `docs/ROADMAP.md` 定义。

## 8. 变更准入规则

以下变更，必须同步改文档：

- 协议结构变化
- 参数范围变化
- IPC 契约变化
- UI 状态或行为变化
- Harness 执行链路变化
- 现场配置字段变化

以下变更，必须同步考虑 skill：

- 出现了重复排障路径
- 出现了稳定可复用的检查顺序
- 出现了重复执行的脚本化套路

## 9. 自我进化机制

NetMic 的自我进化分两种：

### A. 主线进化

进入 `docs/` 的正式文档：

- 产品边界
- 执行模型
- 执行链路
- 协议
- UI/IPC
- 配置

这部分是长期事实来源。

### B. 技巧进化

进入 `.codex/skills/` 的项目私有 skill：

- 复用方法
- 排障套路
- 检查顺序
- 稳定脚本工作流

这部分是长期工作方法。

规则：

- 事实进入 `docs/`
- 方法进入 `.codex/skills/`

## 10. Skill 进入条件

只有同时满足以下条件，某个技巧才应该升级为项目私有 skill：

- 来自真实 run 或真实问题
- 至少具备可复用性
- 输入条件清楚
- 步骤清楚
- 成功与失败信号清楚
- 不属于正式规格文档内容

skill 使用 Codex 标准结构维护：

- `.codex/skills/<skill-name>/SKILL.md`
- 可选：`agents/openai.yaml`
- 可选：`scripts/`、`references/`、`assets/`

## 11. 用户与 Agent 的分工

用户负责：

- 提供方向
- 提供现场信息
- 补充缺失能力
- 决定网络和机器使用方式

Agent 负责：

- 按主线推进
- 把改动接入 Harness
- 把流程写进文档
- 把复用技巧升级成 skill
- 用统一产物给出结论
- 在未完成全部里程碑之前持续推进
- 仅在配置阻塞时向用户请求补充信息

## 12. 项目能持续开发的条件

只要以下结构成立，项目就能持续推进：

- `MVP.md` 还在定义边界
- `docs/OPERATING_MODEL.md` 还在定义总控机制
- `docs/HARNESS.md` 还在定义统一执行面
- `docs/ROADMAP.md` 还在定义推进顺序
- `docs/MODULE_OWNERS.md` 还在定义模块边界
- `docs/PROTO.md` / `docs/UI.md` 还在定义接口
- `docs/ENV.md` + `.harness/hosts.env` 还在承接现场配置
- `.codex/skills/` 还在承接可复用技巧

这就是后续持续开发的最小闭环。
